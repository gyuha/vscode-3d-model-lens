# 화면 기준 회전을 위해 `ArcRotateCamera` 를 버린다 — 격자가 기울어지는 것을 대가로 받는다

좌우 방향키(와 좌우 드래그)가 "물체를 화면 기준으로 돌리는 것"처럼 느껴지지 않고 "위에서 팽이처럼
돌리는 것"처럼 느껴진다는 문제를 풀기 위해, **자유 자세(쿼터니언) 카메라로 옮기기로 했다.**
`ArcRotateCamera` 는 `alpha`/`beta` 로만 자세를 표현하고 **롤 파라미터가 없어서** 화면 기준 회전을
표현할 수 없다.

## 왜 중간 지점이 없는가 (측정값)

`ArcRotateCamera` 의 좌우 회전은 **월드 Y 축** 기준이고, 화면의 수직축(카메라 up)은 월드 Y 에서
`90° − beta` 만큼 벗어나 있다. 입력 `θ` 에 대해 관계식이 이렇다:

**시선 방향 변화 ≈ θ·sin β · · · 화면 롤 ≈ θ·cos β**

`NullEngine` 으로 입력 `5.73°` 에 대해 실측한 값:

| 카메라 각도 | 시선 방향 변화 | 화면 롤 |
|---|---|---|
| `beta = 90°` (수평) | `5.73°` | `0.00°` |
| `beta = 72°` (기본) | `5.45°` | `1.77°` |
| `beta = 34°` | `3.23°` | `4.73°` |
| `beta = 11.5°` | `1.14°` | `5.62°` |
| `beta = 2.9°` | `0.29°` | `5.72°` |

두 값이 같아지는 지점이 정확히 `beta = 45°` 이고, **그 아래부터 롤이 이긴다** — 시선은 거의 안
움직이고 화면만 돈다. 그것이 "제자리에서 도는" 증상의 정체다.

## 기각한 대안 두 개 — 같은 우회를 다시 시도하지 않도록

**(1) `beta` 를 극점에서 떨어뜨린다 (클램프 복원).** 격자가 수평으로 유지되고 변경이 몇 줄이다.
기각 이유: 증상을 실제로 없애려면 위 관계식에 따라 `beta ∈ [45°, 135°]` 로 묶어야 하고, 그러면
**위에서 내려다보는 시야를 잃는다.** 3D 뷰어에서 top view 상실은 회전 감각보다 큰 손실이며,
완화 수단도 없다. 게다가 `v0.1.1` 에서 사용자 요청으로 제거한 한계를 되돌리는 것이다.

**(2) 카메라 up 축으로 위치를 돌린 뒤 `alpha`/`beta` 를 재유도한다.** 방향 변화가 어느 각도에서든
`θ` 로 일정해지므로 그럴듯해 보인다. **측정으로 기각했다 — 롤이 오히려 폭발한다:**

| 카메라 각도 | 이 방식의 방향 변화 | 이 방식의 롤 |
|---|---|---|
| `beta = 34°` | `5.73°` | `8.30°` |
| `beta = 11.5°` | `5.73°` | **`26.22°`** |
| `beta = 2.9°` | `5.73°` | **`63.38°`** |

이유가 근본적이다: **up 을 월드 Y 에 묶어 두면 극점 근처에서 up 자체가 ill-conditioned** 라서,
방향이 조금 바뀌어도 재유도된 up 이 크게 돌아간다. 따라서 **월드 Y 고정 up 을 유지하는 어떤
방식도 이 문제를 못 푼다.** 이건 취향이 아니라 기하학이다.

## 받아들인 대가

- **바닥 격자가 임의 각도로 기울어진다.** `chrome.ts` 의 격자는 월드 Y 고정 XZ 평면이므로
  자유 자세에서 함께 기운다. 실제 렌더로 확인한 뒤 **그대로 두기로** 결정했다 — 기울어진 격자가
  자유 자세에서 "월드의 위가 어디인지" 알려주는 **유일한 단서**이기 때문이다(축 기즈모는
  장식으로 판단해 task 9 에서 제거했다). 격자를 숨기면 방향 단서가 0 이 된다.
- **"시야 수평 복귀" 명령을 넣지 않는다.** 자유 자세는 3자유도라 우연히 수평으로 돌아올 확률이
  사실상 없다는 점을 알고 내린 결정이다. 필요해지면 호출부가 0건인 죽은 코드 `resetView()` 가
  그 자리다(현재는 `target`·`radius` 만 되돌리고 각도는 두므로 각도까지 되돌리도록 고쳐야 한다).
- **포인터·키보드 입력을 직접 짜야 한다.** Babylon 의 `ArcRotateCamera*Input` 을 못 쓴다.
  `measurement.ts` 의 이동 임계값 기반 탭 판정은 Babylon 의 `POINTERTAP` 을 피해 만든 것이므로
  (ADR `260822-115455c` 계열 설계 노트) 그대로 유효하다 — 새 입력이 `POINTERDOUBLETAP` 을
  등록하지 않으면 오히려 제약이 사라진다.
- **저장 상태의 카메라 모양이 바뀐다.** `VIEWER_STATE_VERSION` 은 **올리지 않는다** —
  올리면 카메라 하나 때문에 사용자의 측정값까지 버린다(task 9 가 같은 판단을 기록했다).
  옛 `alpha/beta` 모양은 검증에 실패해 카메라만 버려지고 자동 프레이밍으로 떨어진다.
- **`v0.1.1` 의 연속 수직 회전은 흡수된다.** 쿼터니언 자세에서는 극점이 특별하지 않으므로
  `beta` 한계 제거라는 특수 처리가 필요 없어진다. 그 회귀 장치(e2e 3개)는 `alpha`/`beta` 를
  단정하므로 **새 카메라의 관측값으로 다시 써야 한다 — 지우면 안 된다.**
- **관성(`inertia = 0.9`)은 유지한다.** 요청 범위는 회전 축이고 체감 변화를 끼워 넣으면 문제가
  생겼을 때 원인을 분리할 수 없다. 렌더 게이트가 관성 감쇠에 얽혀 있는 것도 그대로 지킨다.
