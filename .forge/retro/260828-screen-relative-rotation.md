# 회고 — 회전을 화면 기준으로 바꾼다 (자유 자세 카메라)

- 작업: `screen-relative-rotation` (task 15)
- 일자: 2026-08-26 ~ 2026-08-28
- 결과: `verified: yes` — 유닛 124→130, e2e 53→55, 절대 방향 테스트 2개 신규

## 계획 대비 발산

`run.md` 에 7건을 적었다. 여기서는 문서로 승급할 값이 있는 것만 다시 쓴다.

**1. 관성 메커니즘을 계획과 다르게 잡았다.** Babylon 은 입력을 속도에만 넣고 매 프레임 감쇠하므로
입력 `θ` 하나가 `10θ` 만큼 돈다. 충실히 이식하면 드래그가 손가락을 따라가지 않는다. 직접
조작(1:1)과 꼬리(`glide`)를 분리했고 계수 `0.9` 는 유지했다. **ADR 에 승급했다.**

**2. 계획에 없던 보존 항목을 호출부 조사에서 발견했다** — `panSpeed = radius / 2`(사용자가
`0.1.1`·`0.1.2` 에서 직접 넣은 보정). 계획의 비목표는 "버튼 매핑 변경 없음"만 적었다.
**호출부를 먼저 전부 훑은 것이 유일한 발견 경로였다.**

**3. 스펙 파일 뒤쪽을 통째로 자르다가 사용자의 e2e 두 describe(테스트 5개)를 지웠다.**
`v0.2.0` 의 패널 아코디언·패널 숨김 테스트다. 발견 경로는 순전한 운이었다 — typecheck 가
`PANEL_SECTIONS`·`toggleSection` import 를 미사용으로 잡아준 것뿐이고, 그 import 가 없었다면
e2e 53→48 을 "전부 통과"로 보고했을 것이다.

## 깨진 전제 — 둘이고, 같은 뿌리다

**(1) "실측했으면 안전하다"가 아니라 "무엇을 실측했는가"가 문제였다.**
이 작업에서 잰 것은 전부 맞았다 — `θ·sin β` 관계식, `triangleFromPick` 의 월드 행렬 사용,
`upVector` 가 setter 라는 것, 로더의 순변환. **틀린 것은 전부 재지 않고 추론한 것이었다**:
마우스 드래그 방향(재지 않음), Playwright 트레이스 가설(재지 않음), 그리고 아래 (2).
이건 직전 회고(`260822-162443`)가 이미 적은 교훈인데 **또 반복했다.**

**(2) 사용자 보고를 원인 판정으로 직행시켰다 — 이번 작업 최대의 실수.**
"물체가 내가 보는 축으로 회전한다"는 보고를 받고, 실측으로 트랙볼의 성질(기울면 좌우가 고도를
젖힘)을 확인한 뒤 **그것이 원인이라고 단정**했다. 그래서 되돌리기 계획(task 16)을 그릴링까지
마쳤다. 실제 원인은 **조작 부호가 두 축 모두 반대**였던 것이다.

내가 확인한 트랙볼의 성질은 **사실이었지만 원인이 아니었다.** 증상과 양립하는 사실을 하나
찾았다고 원인이 되지 않는데, 그 구별을 하지 않았다. **하마터면 기능 전체와 `v0.1.1` 의 연속
수직 회전까지 잘못된 근거로 되돌릴 뻔했다.**

## 다음에 다르게 할 것

1. **조작 방향은 절대 기준으로 테스트한다 — "서로 같은가"만으로는 부족하다.**
   내가 쓴 `방향키 회전 방향` 은 "키와 드래그가 서로 같은 방향인가"만 단정했다. 카메라 모델을
   바꿔도 유효하도록 일부러 절대 방향을 뺐고, **그 선택이 두 축 전역 반전을 초록으로 통과시켰다.**
   상대 규약 테스트와 절대 규약 테스트는 **둘 다 필요하다.** (`회전 방향 규약 (절대 방향)` 으로
   코드에 굳혔고 ADR 에도 적었다.)
2. **"조작이 손을 따라가는가"를 다른 모든 판정보다 먼저 확인한다.**
   조작이 반대인 상태에서는 회전 모델·감도·관성 어느 것도 공정하게 판정할 수 없다. 사용자 보고가
   모호할 때 가장 먼저 배제해야 할 가설이고, 가장 싸게 확인된다.
3. **증상과 양립하는 사실을 찾으면 "원인 후보"로만 두고, 더 싼 후보를 먼저 배제한다.**
   이번에 트랙볼의 성질은 크고 그럴듯한 설명이었고 실측 근거까지 있었다. 그래서 2글자짜리 부호
   버그를 보지 못했다. **설명의 크기와 원인일 확률은 무관하다.**
4. **파일 뒤쪽을 통째로 자르는 편집을 하지 않는다.** 잘라내기 전에 그 구간에 무엇이 있는지 세거나,
   앵커 기반 치환만 쓴다. 이번엔 typecheck 가 우연히 잡았을 뿐이다.

## 잘 된 것

- **TDD 가 두 번 값을 냈다.** 불변식 테스트의 red 가 계획에 적힌 실측 표를 그대로 재현했고,
  핵심 수정이 **곱셈 순서 한 줄**임을 드러냈다. 부호 버그도 절대 방향 테스트를 먼저 써서 red 를
  본 뒤 고쳤다.
- **직접 짠 포인터 입력의 위험을 기존 회귀 장치가 덮었다.** 측정·정점 스냅 e2e 가 실제 포인터로
  `probeAt` 을 구동하므로, 입력을 새로 쓴 것이 측정을 깨지 않았음을 실행으로 확인했다.
- **게시를 UAT 뒤로 미룬 것이 실제로 값을 했다.** `v0.3.0` 은 커밋·push 됐지만 게시하지 않았고,
  그 사이에 부호 버그가 드러났다. 게시했다면 반대로 도는 조작이 사용자에게 나갔을 것이다.
